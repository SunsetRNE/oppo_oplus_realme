# 🎛️ 统一编译调度体系（档案驱动版）

> 目标：**单入口、全中文、不动编译体系**地统一触发三平台编译
> 架构：参数配置生成器 → 参数存放集 → 读取参数触发器（Producer → Queue → Consumer）
> 核心：**链式触发器**——每个编译工作流匹配专属验证过的配置档案（config/profiles/），严苛一对一
> 状态：✅ 档案驱动版（21 个档案已建档，待人工校准 verified）

---

## 一、架构总览

```
┌─────────────────┐      ┌──────────────────┐      ┌──────────────────┐
│ 生成器 Producer  │ ───► │ 存放集 Queue     │ ───► │ 触发器 Consumer  │
│ compile_        │ 入队 │ queue/ 目录      │ 消费 │ compile_trigger  │
│ dispatcher.yml  │      │ (pending/running │      │ .yml (cron/5min) │
└────────┬────────┘      │  /done/failed)   │      └────────┬─────────┘
         │ ①选工作流      └──────────────────┘               │ dispatch
         │ ②加载档案      完整标准 JSON（已解压）             ▼
         │ ③解压 inputs                       sm*_fastbuild_*.yml（编译体系，零改动）
         ▼
    config/profiles/（人工维护的验证档案库，链式触发器的"链"）
```

| 组件 | 文件 | 职责 |
|---|---|---|
| 生成器 | `.github/workflows/compile_dispatcher.yml` + `scripts/dispatcher/generate_tasks.py` | 中文表单（首选项=工作流）→ 加载档案 → 严苛匹配校验 → 解压完整 inputs → 规则校验 → 入队（**不触发编译**） |
| 档案库 | `config/profiles/<工作流文件名>.json` | 人工维护的**验证资产**：文件名=匹配键，变体预留单档；无档案的工作流**不显示、不触发、不警告** |
| 存放集 | `queue/{pending,running,done,failed}/` | 任务状态机：待处理 / 处理中 / 完成 / 失败 |
| 触发器 | `.github/workflows/compile_trigger.yml` + `scripts/dispatcher/consume_tasks.py` | 每 5 分钟扫描 → 消费到期任务（默认每轮 2 个）→ workflow_dispatch 注入参数 → 结果写回 |

## 二、使用方式（三步）

1. **Actions → 统一编译生成器（档案驱动·参数入队）** → Run workflow
   - **① 选择工作流**（下拉仅列有档案的；无档案=无链=不显示）
   - ② 后缀模式（留空/自动/自定义，自定义**禁止空格**）
   - ③ 延迟触发时间（可选）
2. 生成器自动：加载所选工作流的档案 → 解压完整 inputs → 校验（422 防错 / lz4·lz4kd 互斥 / ksu 禁用 / 后缀禁空格）→ 写入 `queue/pending/`
3. **触发器**（每 5 分钟自动）消费任务 → 逐个触发编译 → 完成后写回 `queue/done/`

> 手动立即消费：Actions → **统一编译触发器** → Run workflow（可调 batch_size）
> 微调参数：**不分裂档案**——直接手动触发对应编译 workflow（收益更大，档案保持纯净）

## 三、任务 JSON 格式（存放集内标准契约）

```json
{
  "task_id": "20260804150000_sm8850_61223",
  "workflow": "sm8850_fastbuild_6.12.23.yml",
  "platform": "sm8850",
  "version": "6.12.23",
  "ref": "main",
  "inputs": { "ksu_type": "resukisu", "susfs_enable": true, "kernel_suffix": "SunsetRNE_20260804150000_12345" },
  "delay_until": "2026-08-04T15:00:00+08:00",
  "max_retry": 2,
  "retry_count": 0,
  "source": "profile",
  "profile_verified": false,
  "created_by": "compile_dispatcher",
  "created_at": "2026-08-04T14:50:00+08:00"
}
```

> inputs 永远来自**档案解压后的完整参数**（压缩表达→解压在生成器内部完成，queue/触发器只见标准 JSON）

## 四、核心设计决策

| 决策 | 说明 |
|---|---|
| 链式触发器 | 每个编译工作流匹配**专属验证过的档案**（文件名即匹配键，档案内 workflow 字段双重校验）；无档案=无链=不显示/不触发/不警告 |
| 压缩表达 | 生成器表单只暴露 4 个 input（工作流/后缀模式/自定义后缀/延迟），远低于 GitHub 显示上限（~10）；13 个编译参数全部藏在档案里，选工作流自动解压 |
| 档案人工维护 | 档案是**验证资产**（不同配置在不同手机会黑屏/无限重启，只有正确配置能开机）；本地拉取修改、失效即删、跑 gen_profiles.py 重新生成 |
| 变体预留单档 | 档案 JSON 保留 `variants` 结构，当前每工作流仅 1 个 default 档；微调不分裂档案 |
| 规则表特判 | `kernel_suffix` 是唯一带自由文本约束的 input：正则 `^[A-Za-z0-9_]+$` + 长度 ≤64 + 三分支（留空/自动/自定义），**错误输入进不了队列** |
| 档案漂移防护 | 生成器校验档案 inputs 与编译 workflow 实际 inputs 一致性：缺必填→中止（档案过期）；多余→警告丢弃 |
| 中文只在一层 | 中文（表单）只在生成器；queue 与触发器全英文标准 JSON → 触发器零解析、零改动 |
| 并发天然受限 | 触发器每轮消费 `batch_size`（默认 2）→ 21 个任务约 1 小时串完，不碰 runner 上限 |
| 延迟触发 | 任务 `delay_until` 字段（UTC+8），未到期跳过 |
| 幂等恢复 | 触发器崩溃后，下次 cron 重扫 running/ 查 run 状态继续（先写 running 占位再 dispatch） |
| 无需 PAT | 同仓库 GITHUB_TOKEN（contents: write + actions: write）即可 |

## 五、目录结构

```
scripts/dispatcher/
├── common.py                 # API封装 / 动态解析 / 业务规则表 / 队列读写 / 档案加载校验
├── generate_tasks.py         # 生成器：选档案→解压→校验→入队（--dry-run 预检）
├── consume_tasks.py          # 触发器：恢复running→消费pending→dispatch→写回done（--batch N）
├── gen_profiles.py           # 档案生成器：从 workflow YAML 默认值建档（自动同步表单选项）
└── sync_profile_options.py   # 档案注册表同步器：档案增删→重写生成器表单选项
config/
├── profiles/                 # 档案库（人工维护，文件名=工作流名.json）
└── compile_task.example.yml  # 中文任务模板（入口B：文件驱动，预留扩展）
queue/{pending,running,done,failed}/   # 参数存放集（状态机目录）
```

## 六、档案维护流程（人工）

```
1. 本地拉取仓库 → 修改/新增/删除 config/profiles/*.json
2. 档案结构：{ workflow(匹配键), platform, version, verified, variants: { default: {13个inputs} } }
3. 已实测能开机的配置 → verified 置 true（校准完成）
4. 失效档案 → 直接删除（无档案=不显示=不会误触发）
5. 跑 python3 scripts/dispatcher/gen_profiles.py 可重新生成默认值档案（会覆盖，慎用）
   —— 档案增删后自动同步生成器表单选项（有档案才显示）
```

## 七、已知限制与后续优化

- [x] **done/ 清理**：触发器每轮清理 30 天前的 done 文件（每轮限量 10 个，防仓库膨胀）
- [x] **failed/ 自动重投**：失败结论（failure/cancelled/timed_out 等）按 `max_retry` 自动重投 pending（清 run_id 重新触发），耗尽后归档 failed/
- [x] **Release tag 回填**：done 记录 run 结论 + 正式发布 Release tag（按 head_sha 匹配 `OPPO-OPlus-Realme-build-*`）
- [x] **队列看板**：触发器 summary 输出 markdown 看板（四队列统计 + 最近完成/失败记录）
- [ ] **串行模式**：batch_size=1 时即纯串行（最保守）；可加"等待前一批完成再消费下一批"选项
- [ ] 触发器写操作均为 Contents API 单文件操作（创建=PUT/删除=DELETE），非原子移动（先写目标再删源），已按幂等设计

## 八、安全边界

- 生成器/触发器均不接触 PAT；只用 GITHUB_TOKEN（仓库内自动注入，作用域受 permissions 限制）
- 触发器不解析用户自由文本（只消费标准 JSON），注入编译 workflow 的参数**全部经过白名单清洗 + 规则校验**
- 触发权限：`actions: write`（dispatch）+ `contents: write`（queue 文件）
- 档案由人工维护，无自动初稿机制（避免测试噪音干扰判断）
